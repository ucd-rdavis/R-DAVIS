Writing functions

You have been using functions since week 1: mean(), filter(), ggplot(), read_csv(). Each one is code that someone wrote once, gave a name, and shared so nobody has to rewrite it.

library(tidyverse)

Our data: electricity generation by country

This week we use electricity data from Our World in Data, which compiles it from Ember and the Energy Institute. Each row is one country in one year, 2000–2024. For each country-year we have total electricity generated, the amount from each of nine sources (coal, gas, oil, nuclear, hydro, wind, solar, bioenergy, and other renewables), population, and the carbon intensity of the electricity. Electricity is measured in terawatt-hours (TWh). One TWh is one billion kilowatt-hours (kWh).

The codebook describes every column.

Why write functions?

There are many reasons, but they tend to come down to accuracy, convenience, and speed. When you write a custom function instead of script out a process multiple times, there is only one place for mistakes and one place to fix them. Your scripts get shorter, you can reuse the function for other applications, and you can build on the function with other functions to scale up your code.

A common rule of thumb: once you have copied a block of code twice, write a function.

The parts of a function

Here is a function that calculates a percentage:

pct <- function(part, total) {
  100 * part / total
}

It has four parts:

  • Name: pct. You assign a function to a name with <-, like any other object.
  • Arguments: part and total, listed inside function(). These are the inputs.
  • Body: the code between the curly braces { }. It uses the arguments.
  • Return value: the output. R returns the value of the last line of the body.

Running that chunk does not calculate anything. It creates an object called pct in your Environment, with type function. The body runs only when you call the function:

pct(1, 4)
## [1] 25
pct(part = 30, total = 120)
## [1] 25

When you call pct(1, 4), R sets part to 1 and total to 4, runs the body, and returns the result.

Because the body only uses arithmetic, which works on whole vectors, pct() also works on vectors:

pct(c(10, 20, 30), 200)
## [1]  5 10 15

You can also call your function–just like other functions you already know of–inside mutate():

elec_pct <- elec %>%
  mutate(coal_pct  = pct(coal_electricity,  electricity_generation),
         wind_pct  = pct(wind_electricity,  electricity_generation),
         solar_pct = pct(solar_electricity, electricity_generation))

elec_pct %>%
  filter(country == "Norway", year %in% c(2000, 2012, 2024)) %>%
  select(country, year, coal_pct, wind_pct, solar_pct)
## # A tibble: 3 × 5
##   country  year coal_pct wind_pct solar_pct
##   <chr>   <dbl>    <dbl>    <dbl>     <dbl>
## 1 Norway   2000   0.0281   0.0210     0    
## 2 Norway   2012   0.0274   1.05       0    
## 3 Norway   2024   0        9.29       0.337

Tip

You can also end a function with return(x). R automatically returns the last evaluated expression in a function, so return(x) is not necessary. But sometimes, you might want to use return(x) to have the function return not the last thing under certain conditions.

divide_numbers <- function(a, b) {
  if (b == 0) {
    return(NA) # Stops immediately so it doesn't divide by zero
  }
  a / b        # Implicitly returned if b is not 0
}


Arguments and default values

You can give an argument a default value in function(). If the user doesn’t supply that argument, the default is used. round() does this: digits defaults to 0. Let’s add a digits argument to pct():

pct <- function(part, total, digits = 1) {
  round(100 * part / total, digits)
}

pct(1, 3)
## [1] 33.3
pct(1, 3, digits = 3)
## [1] 33.333

R matches arguments by name first, then by position. These calls give the same result:

pct(1, 3, 2)
## [1] 33.33
pct(total = 3, part = 1, digits = 2)
## [1] 33.33

Naming every argument after the first one or two makes your code easier to read, especially for arguments like digits that change how a function behaves.

From working code to a function

Most functions start as code that works for one case. The steps are:

  1. Write code that works for one case.
  2. Find the values you would change to run it for a different case.
  3. Replace those values with arguments and wrap the code in function().
  4. Test the function on the original case, then on a new one.

Let’s build a function that shows a country’s electricity mix (the share from each source) in one year.

Step 1: write it once. Here is Norway in 2024. We pivot the nine source columns into a long table (week 5), clean up the source names, and use pct():

elec %>%
  filter(country == "Norway", year == 2024) %>%
  pivot_longer(coal_electricity:other_renewable_electricity,
               names_to = "source", values_to = "twh") %>%
  mutate(source = str_remove(source, "_electricity"),
         share = pct(twh, electricity_generation)) %>%
  select(source, twh, share) %>%
  arrange(desc(share))
## # A tibble: 9 × 3
##   source             twh share
##   <chr>            <dbl> <dbl>

## 2 wind             14.6    9.3

Step 2: find what changes. To run this for a different country or year we would edit "Norway" and 2024. Those become arguments. We also make the data an argument, so the function doesn’t depend on an object called elec existing.

Step 3: replace and wrap.

elec_mix <- function(data, country_name, yr) {
  data %>%
    filter(country == country_name, year == yr) %>%
    pivot_longer(coal_electricity:other_renewable_electricity,
                 names_to = "source", values_to = "twh") %>%
    mutate(source = str_remove(source, "_electricity"),
           share = pct(twh, electricity_generation)) %>%
    select(source, twh, share) %>%
    arrange(desc(share))
}

Don’t name arguments after columns

Notice the argument is called country_name, not country. Here is what happens if you use country:

elec_mix_bad <- function(data, country, yr) {
  data %>%
    filter(country == country, year == yr)
}

elec_mix_bad(elec, "Norway", 2024) %>% nrow()
## [1] 199

We asked for one country and got every country. Inside filter(), dplyr looks for column names first. country == country compares the country column to itself, which is always TRUE. Give arguments names that are not column names in your data.

Organizing functions

What happens in a function stays in the function

Objects created inside a function exist only while it runs. Changes you make to an argument inside a function do not change the original object. For instance, the code below filters data, the function’s own copy of its input, but leaves elec, the object we passed in, unchanged. And n_rows disappears when the function finishes.

count_2024 <- function(data) {
  data <- filter(data, year == 2024)
  n_rows <- nrow(data)
  n_rows
}

count_2024(elec)
## [1] 199
nrow(elec)    # elec still has every year
## [1] 5459
n_rows        # this only existed inside the function
## Error:
## ! object 'n_rows' not found

The function worked on a copy of elec. This makes functions safe to use: calling one won’t change your data unless you save its output with <-.

It works the other way too. A function can see objects in your Environment, so elec_mix() would still run if we deleted its data argument and wrote elec in the body. Don’t do this. A function that only uses its arguments gives the same answer no matter what else is in your Environment, and it works on any data you pass to it.

Habits for writing functions

A few habits that make functions easier to use later:

  • Name functions with what they do: elec_mix(), kwh_per_person(). Avoid names like f1() or my_function().
  • Write a short comment above each function saying what goes in and what comes out.
  • Keep each function to one job. If you can’t describe it in one sentence, split it up.
  • Put the data argument first, so the function works with %>%.
# Percent of total. Returns 100 * part / total, rounded to `digits`.
pct <- function(part, total, digits = 1) {
  round(100 * part / total, digits)
}

Keeping functions in their own script

As you write more functions, keep them in a separate script, such as scripts/functions.R, rather than at the top of your analysis. Then load them all with source():

source("scripts/functions.R")

source() runs every line of the file, so your functions appear in the Environment, ready to use. Your analysis script stays short, and you can reuse the same functions.R in other projects.

Improving functions

Test with values you know

Before you trust a function, try it on inputs where you already know the answer:

pct(50, 200)     # should be 25
## [1] 25
pct(0, 200)      # should be 0
## [1] 0
pct(NA, 200)     # missing in, missing out
## [1] NA
pct(0, 0)        # 0 divided by 0
## [1] NaN

The last one returns NaN (“not a number”). That is not just a math curiosity: a few rows in our data report 0 total generation. You don’t have to handle every odd case, but you should know what your function does with them.

compare_years <- function(data, country_name, year1, year2) {

  second <- elec_mix(data, country_name, year2) %>% select(source, share_2 = share)

Passing column names: {{ }}

So far our arguments have been values: a country name, a year. Sometimes you want an argument to be a column. For example, a function that lists the top countries for any column we choose. Here is a first try:

top_countries <- function(data, col, yr, n = 5) {
  data %>%
    filter(year == yr) %>%
    arrange(desc(col)) %>%
    select(country, col) %>%
    head(n)
}

top_countries(elec, wind_electricity, 2024)
## Error in `arrange()`:
## ℹ In argument: `..1 = col`.
## Caused by error:
## ! object 'wind_electricity' not found

R can’t find wind_electricity. dplyr functions let you type bare column names like wind_electricity, but that only works when the column name is typed directly into the dplyr function. Here, dplyr sees col, looks for a column called col, doesn’t find one, and fails.

The fix is to wrap the argument in double curly braces, {{ col }}. This tells dplyr to use the column that the user passed in:

top_countries <- function(data, col, yr, n = 5) {
  data %>%
    filter(year == yr) %>%
    arrange(desc({{ col }})) %>%
    select(country, {{ col }}) %>%
    head(n)
}

top_countries(elec, wind_electricity, 2024)
## # A tibble: 5 × 2
##   country        wind_electricity
##   <chr>                     <dbl>
## 1 China                     997. 
## 2 United States             452. 
## 3 Germany                   142. 
## 4 Brazil                    108. 
## 5 United Kingdom             83.3
top_countries(elec, carbon_intensity_elec, 2024, n = 3)
## # A tibble: 3 × 2
##   country      carbon_intensity_elec
##   <chr>                        <dbl>
## 1 Turkmenistan                 1306.
## 2 Uzbekistan                   1040.
## 3 Montserrat                   1000

{{ }} also works inside mutate(), summarize(), and group_by(). You only need it when a function argument stands for a column name.

It works with columns you create, too:

elec %>%
  mutate(wind_pct = pct(wind_electricity, electricity_generation)) %>%
  top_countries(wind_pct, 2024)
## # A tibble: 5 × 2
##   country   wind_pct
##   <chr>        <dbl>
## 1 Denmark       58.2
## 2 Lithuania     46.1
## 3 Uruguay       38.6
## 4 Ireland       37.3
## 5 Djibouti      35

Challenge

Write a function avg_by_country(data, countries, col) that returns the mean of col (generic column name) across all years for each country in countries. Use it to compare carbon intensity in Norway, Sweden, and Finland.

Hint: countries can hold more than one name, so use %in% instead of == in filter().

ANSWER 
avg_by_country <- function(data, countries, col) {
  data %>%
    filter(country %in% countries) %>%
    group_by(country) %>%
    summarize(mean = mean({{ col }}, na.rm = TRUE))
}
avg_by_country(elec, c("Norway", "Sweden", "Finland"), carbon_intensity_elec)
## # A tibble: 3 × 2
##   country  mean
##   <chr>   <dbl>
## 1 Finland 228. 
## 2 Norway   31.2
## 3 Sweden   46.2


Checking inputs

What happens if we misspell a country?

elec_mix(elec, "Nrway", 2024)
## # A tibble: 0 × 3
## # ℹ 3 variables: source <chr>, twh <dbl>, share <dbl>

We get an empty table and no warning. In a long script, that can go unnoticed. A function can check its inputs and stop with a clear message. To do that we use if and stop():

elec_mix <- function(data, country_name, yr) {
  if (!country_name %in% data$country) {
    stop("Can't find '", country_name, "' in the data. Check the spelling.")
  }
  data %>%
    filter(country == country_name, year == yr) %>%
    pivot_longer(coal_electricity:other_renewable_electricity,
                 names_to = "source", values_to = "twh") %>%
    mutate(source = str_remove(source, "_electricity"),
           share = pct(twh, electricity_generation)) %>%
    select(source, twh, share) %>%
    arrange(desc(share))
}

elec_mix(elec, "Nrway", 2024)
## Error in `elec_mix()`:
## ! Can't find 'Nrway' in the data. Check the spelling.

if is different from the ifelse() you saw in week 5. ifelse() works on a whole vector and returns a vector. if takes a single TRUE or FALSE and decides whether to run the code in its braces. Here, if the country is not in the data, stop() ends the function and prints our message.

You don’t need to check every possible input. Check the mistakes that are likely and that would otherwise fail quietly.
